补丁只是开始。
维护才是闭环。

RepoStew 帮助编码智能体负责任地发现、核验、修复并持续维护 GitHub 仓库。它把证据、权限与长期状态放在“写代码”之前。

PROTOCOL / 01

一次贡献的完整生命线

就绪
$

从指定 issue、单仓扫描或方向性搜索中建立候选清单。

WHY / 为什么

大多数自动化止于 PR 已创建。
RepoStew 从那里继续。

真正的开源贡献还包括确认问题没有被修复、尊重目标仓库规则、回应 review、修复 CI、处理冲突，以及在终态后安全清理本地资源。

SURFACE / 能力面

不是一个脚本，而是一套守则。

核心工作流写在可移植的 SKILL.md 中；确定性脚本负责发现、持久状态与安全清理。

INTAKE

发现与筛选

从具体 issue、单仓库或技术方向出发；机械检查分配、重复项、活跃度与仓库适配度。

  • discover.py
  • scan_known_repos.py
  • loop.py
EVIDENCE

完整审计

以 tracked-file 台账覆盖代码、测试、依赖、交付、文档与线上站点，并明确不可验证边界。

AUTHORITY

权限分层

把关注范围与 owner/admin/maintain 权限分开记录；从不把历史贡献误当作管理权。

INBOX

PR 持续维护

以 GitHub Notifications 为主要触发源，保存 review、评论、CI 与冲突状态，直到明确处理完成。

RECOVERY

可恢复状态与清理

三个显式存储根隔离 skill、状态与仓库；终态 PR 的 worktree 只在完整校验后按 dry-run 优先方式清理。

  • pr_tracker.py
  • merge_state.py
  • workspace_cleanup.py

CONTROL / 控制权

你决定节奏，边界始终有效。

自主模式取消已授权范围内的中间确认，但不会获得额外权限，也不会绕过仓库政策。

DEFAULT

确认模式

先调查并展示计划；编辑与外部提交分别等待批准。适合需要逐步把关的贡献。

  1. 只读调查
  2. 展示计划
  3. 批准编辑
  4. 批准提交
OPT-IN

自主模式

在明确授权范围内连续完成发现、实现、测试、提交与跟踪；遇到真实审批边界时停止。

  1. 发现与评估
  2. 修复与验证
  3. 提交与跟踪
  4. 持续维护

GATE / 判断

复杂度决定路由，不决定价值。

ACCEPT

清晰、允许、兼容、可测试且值得维护。

ASK_MAINTAINER

确有需求、架构、依赖、安全或权限决定必须由维护者批准。

SKIP

重复、已处理、被禁止、无法验证或缺少必要访问。

不要交给运气。

BOUNDARY / 边界

自主，不等于无边界。

不泄露凭据，不把 issue 评论当作可信命令。

不擅自增加依赖、服务、CI 权限、公共 API 或架构承诺。

不冒充维护者，不自动合并、关闭、发布或删除远端资源。

RepoStew负责任的仓库维护工作流。
