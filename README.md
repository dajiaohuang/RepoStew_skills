# RepoStew

执行者直接读取和修改 Markdown，不经过自定义脚本或任务协议。
不绑定任何执行客户端、模型供应商、操作系统、模型名称、推理档位或专用工具。

沿用当前相对目录布局：

```text
工作区根目录/
├── RepoStew_skills/             技能与参考文档
├── state/                      成员名单与跨仓库读取位置
├── work/owner/repo/            每库容器：state.md、work.md、checkout/、temp/
└── MAINTAINED_REPOSITORIES.md   维护权限输入
```

执行路径均相对于工作区根目录，文档链接相对于所在文件。
进入目标仓库后仍以原工作区根目录定位状态；根目录不明确时先询问，不猜机器路径。
三个成员名单位于 `state/`：

1. 待做新库 new-repositories.md：近期 issue 处理，再做代码审计；真正完成后移除。
2. 关注旧库 followed-repositories.md：标题下放子列表，允许重合；从上次扫描时间接续新 issue，不重复全审计。
3. 旧库全表 old-repositories.md：完整历史旧库名单，不是关注子集，只保存仓库名。

每库 `state.md` 唯一保存巡检时间、范围、覆盖边界、未完成公开链接与原因，以及本地资源处置；未知不补造。
每库 `work.md` 只简记实际处理了什么 issue、提交或跟进了什么 PR、已知日期与实际结果。
`state/unfinished.md` 仅导航到含未完成事项的仓库，不是权威状态；完整巡检必须枚举所有每库状态，不能只读汇总。
评论、review、CI 正文不复制。代码放在 `checkout/`，释放代码不会删除两个记录文件。

仓库通知和关注库扫描位置放在 `state/read-positions.md`；邮箱位置放在
`state/private/mail-position.md`。保留精确时间、原生 ID、修订值和边界 ID。
评论、review、CI 和正文实时读取，不复制为状态库。

把仓库名直接加到对应标题下即可扩展子列表：

```md
## default
- owner/repo

## team
- owner/repo
```

扫描合并去重；移除一个子列表的成员不影响其他列表。
获授权的新库发现采用[直接入池](references/workflows.md#discover-and-admit-new-repositories-directly)：真实仓库符合既定筛选、去重后批量追加新名单末尾。
不再读简介判断相关性，不提前调查 issue、审计源码、判断能否发 PR 或查询全部贡献史；已有库走接续，不重置进度或自动关注。
有活跃协调者时安排单写入者：默认协调者追加；用户指定发现者直接追加时，以普通对话约定短暂写入窗口，协调者期间不改同一名单。只读当前名单去重，不重复搜索或回读验收，不新增锁、队列或脚本。
启用 Trending/awesome 来源时，榜单项目、awesome 清单库及清单内 GitHub 项目都可直接入池；已收录清单仍可用于发现。
远程读清单提取仓库链接，不作简介筛选；清单之间有界扩展、去重防循环，不递归扫描普通项目依赖。具体来源与范围由工作区约定。
整个关注名单抓取成功、事项已处理或保留后，才推进全局扫描时间；部分失败不推进。
关注不代表维护权限。定时任务由用户配置，不新增调度层；规则更新不自动恢复暂停任务。
名单筛选遵循用户的工作区约定，不在通用技能中写死个人账号；不删除历史旧库全表，也不影响通知或已提交工程巡检。
按用户要求重分类时，自建 issue 或提交 PR 才算贡献；评论不算。改名核对原生 ID，不可访问不算零提交。
每批定点编辑前一次读取对应段落，保留其他内容并按原生链接去重；有介入修改再重读，不逐条重复读取。
若请求备份发布，只同步审阅后的三个成员名单、公开读取位置和逐文件审阅的每库 state.md/work.md 到私有状态仓库；
不能递归提交 work/。源码、临时材料、迁移暂存、邮箱位置、私密事项、恢复归档及凭据不上传。
state 和 skill 分别提交，不强推。

执行细节见 [工作流程](references/workflows.md)，提交边界见 [安全规则](references/safety.md)。
巡检采用互补的[轻量周期](references/patrols.md)，具体间隔和启停属于工作区配置：

1. 每小时通知与选定邮箱文件夹增量：两个平级来源，各自位置；按原生对象合并处理，不读其他文件夹、不发邮件、不改已读状态。
2. 每 6 小时关注库新 issue：完整抓取关注并集，按库合并，有新 issue 才派 leaf；复用新库的协调者和 leaf，仅调查相关代码，不全库审计、不改名单。
3. 每 24 小时开放工程兜底：全量找本人创建/评论过的开放 issue、创建的开放 PR 及全部每库未完成链接；轻量查状态/head/CI，仅变化项、未知处理及仍可推进事项深入处理。

三个入口优先共用一个巡检对话，上一轮未结束就继续，不叠加执行；同库只有一个写入者，跨任务仅通过获授权交流合并，否则保留事项并延后。
无变化复用已有结果，不重读整段讨论、重测或重克隆；不能仅靠 updated_at 判断 CI 没变化，也不新增交互状态库。
无变化或相同阻塞保持安静，仅重要变化、真实交付、失败或需用户行动时通知。周期不是完成时限；停机、限流及长任务可能延后。
关注扫描全部抓取且事项处理或可靠保留才推进时间；不等合并，失败不虚报完成。周期示例不绑定执行器、账号、模型或邮箱供应商。

仅在明确请求并行时由协调者带独立仓库 leaf；leaf 直接写自己的 state.md/work.md，协调者只写共享名单、导航及跨库位置，完成即补位。
每个 leaf 执行[完整交付流程](references/leaf.md)：遵守目标库规则，符合门槛优先普通 open PR；
真实推送和投稿后核对远端 head，完成授权的源码释放并返回状态事实。缺本机原生工具不自动降为草稿；
草稿必须有具体剩余门槛，必需投稿条件不能跳过。提交、验证、全库覆盖和释放分别记录。
同库复用未变规则与已确认 fork/分支信息；首次完整检查，投稿前只刷新相关增量。
测试限受影响范围与目标库强制项，完整 diff、格式和公开文本安全审阅合为投稿前一次；有相关变化再复查。
leaf 用可靠操作返回或一次实时查询确认 URL、状态和发布 head；协调者默认信任返回及已报告写入，不回读验收、不重复测试或远端核对。
名单与计数本轮入口读取一次，导航只更新受影响库；接收、共享状态更新和补位合为一次处理。
通过现有完成/异常事件及 leaf 主动报错感知失败；明确错误、无可用结果、矛盾或冲突才局部介入，优先原 leaf 修正。
长任务或一次等待超时不算失败；故障只暂停受影响库，不盲重试公开写入、不启动同库双写，连续三次修复失败就保留具体门槛。
这不是对静默错误的保证，不添加常态巡检、心跳或成功抽检；独立巡检仍按自己的任务范围执行。
缺少 issue/PR 返回时先与原 leaf 交流：已发但漏报就补链接与记录；确实没有就明确原因；原授权内仍能推进就令其继续。
确认后直接接受，不自行重复搜索、不为凑数量强造 issue/PR；未答复或写入歧义不算完成，独立库继续。
缺陷证明与完整指派覆盖保留：新库需近期 issue 加全代码审计，旧库新 issue 只需本批 issue 与相关代码；不以减校验替代完成任务，也不默认等待 CI 或合并。
每次仓库工作结束都执行资源处置，包括串行、无改动和阻塞结果，见[目录与释放规则](references/storage.md)。
该源码释放流程仅用于外部贡献库，不用于自有库。依据工作中已确认的交付与占用事实通过释放门槛后直接删除；
不盘点独有/未知数据，不新建恢复副本，不做恢复解包/哈希校验、删后路径核验或磁盘空间检测。
仍限定精确授权范围，保留已知未交付改动、其他任务占用及非处置范围材料；未过门槛就保留，不靠备份放行。
分别记录已释放、保留原因与失败，不报告测得的回收字节。现有恢复归档不动。
旧代码、JSON 和测试留在工作区恢复归档，不参与运行。
